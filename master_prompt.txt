# 2. THE ACTUAL PROBLEM WE ARE SOLVING

Bayora is an adversarial AI safety-validation platform built around a continuous Red Team → Blue Team → Target LLM → Evaluation loop.

The official challenge describes a shared Docker-based cloud sandbox and identifies four central concerns:

1. Red Team attack payloads must not be observable by Blue Team before a test concludes.
2. Blue Team defensive logic must not be exposed or inferable by Red Team tooling.
3. The client LLM must remain clean and uncontaminated throughout the evaluation.
4. Safety findings must not be invalidated by environmental leakage or cross-tenant interference.

The challenge asks how adversaries, defenders, and a model under test can operate simultaneously without exposing sensitive state or creating exploitable side channels.

Build Bayora to demonstrate a credible proof of concept for these requirements.

## The three principal actors

**Red Team:** Submits adversarial test prompts and attempts to identify weaknesses in the model and its surrounding defenses. It should receive only the responses and test information explicitly permitted by the evaluation protocol.

**Blue Team:** Configures defensive rules, input filters, output validation, policy enforcement, and other countermeasures. Its private configurations must not be readable through Red Team interfaces or APIs.

**Target LLM:** The client-provided language model being evaluated. Its model version, configuration, session context, and stored state must be protected from unauthorized modification or cross-session contamination.

## The supporting components

- **Bayora Controller:** Coordinates evaluation sessions and mediates all approved communication.
- **Policy Engine:** Applies input and output defenses.
- **Model Gateway:** Provides a controlled interface to an approved target model.
- **ShadowPolicy Evaluator:** Measures whether an attacker can infer confidential policy information from observable behavior.
- **Audit Collector:** Receives security events and verifies their integrity.
- **Observability Engine:** Detects suspicious access, policy violations, network attempts, and resource anomalies.
- **Evaluation and Reporting Engine:** Scores test outcomes, calculates metrics, and produces reproducible reports.

Treat this as a security engineering project with explicit trust boundaries, not just a functional AI application.

# 3. PRODUCT VISION AND DIFFERENTIATION

The main product is Bayora. ShadowPolicy is a distinctive proposed evaluation module within Bayora, not the entire product.

## Bayora's core value

Bayora lets organizations evaluate a language model and its safeguards in a controlled adversarial environment.

It should help answer:

- Can the target model be manipulated through adversarial prompts?
- Can the defenses prevent or detect unsafe outputs?
- Can Red Team discover information about Blue Team's hidden policies?
- Can one evaluation session contaminate another?
- Can a team access resources outside its permissions?
- Can the security team reconstruct what occurred from the audit trail?
- Are the measured outcomes repeatable and reliable?
- What risks remain even after the defenses are enabled?

## ShadowPolicy: the proposed differentiating feature

Implement **ShadowPolicy — Blind Policy-Leakage Evaluation**.

ShadowPolicy investigates whether Red Team can infer hidden defense configuration from permitted observations without directly accessing the defensive configuration.

For example, a defensive service may apply a secret rule to certain categories of request. Red Team can see whether a request is accepted, rejected, rewritten, or returned with an error. Differences in response content, status, or timing may reveal information about the hidden policy.

ShadowPolicy must:

1. Create a test round with hidden synthetic policy facts.
2. Commit cryptographically to the policy set before Red Team begins.
3. Allow Red to submit a limited number of controlled probes.
4. Expose only the observations permitted by the round configuration.
5. Allow Red to submit and lock its guesses.
6. Prevent disclosure of the hidden ground truth before the round is finalized.
7. Reveal the ground truth to an authorized evaluator after the round ends.
8. Verify the initial commitment against the revealed policy set.
9. Calculate policy-inference and response-leakage metrics.
10. Compare results before and after Blue enables mitigations.

The purpose is to measure the inferability of hidden policies, not to claim that a particular feature has never existed elsewhere.

All initial policies should be synthetic demonstration policies, not real credentials, commercial secrets, or dangerous infrastructure details.

The application must distinguish policy information that is intentionally revealed after a completed round from information that leaks prematurely during testing.

- Accepts adversarial testing instructions.
- Provides a test workbench.
- Submits probes through the controller.
- Tracks its own allowed requests and results.
- Enforces probe quotas and request size limits.
- Cannot inspect Blue Team code, private policy files, audit storage, model weights, or hidden evaluation state.

### Blue Policy Service

- Stores versioned defense rules.
- Applies input validation and prompt-injection checks.
- Runs output validation.
- Supports configurable response normalization.
- Records detection and mitigation decisions.
- Exposes safe operational summaries to authorized Blue Team members.
- Never exposes private policy definitions through Red Team endpoints.

### Model Gateway

- Supports registered model adapters.
- Attaches a stable evaluation ID and model version to each execution.
- Ensures that test sessions receive isolated context.
- Enforces maximum input/output sizes and request timeouts.
- Forwards approved requests only.
- Does not permit arbitrary shell commands, tools, or network actions from generated model output.
- Records model errors and execution metrics.

### Evaluation Service

- Executes test suites.
- Correlates outcomes with the target model and defense versions.
- Calculates metrics from recorded results.
- Separates direct model vulnerabilities from infrastructure failures.
- Generates reports with clear evidence references.

### Audit Collector

- Receives structured security events.
- Assigns sequence numbers and trusted timestamps.
- Calculates a chained hash for each event.
- Periodically verifies hash integrity.
- Produces signed checkpoints if signing keys can be kept outside the tenant services.
- Does not expose arbitrary update or delete APIs to Red or Blue.
- Produces an integrity status and identifies verification failures.

Do not describe a hash-chained file as truly immutable. Use the terms “tamper-evident” and “integrity-verifiable” unless independent storage controls and administrative boundaries actually support a stronger claim.

# 7. SHADOWPOLICY IMPLEMENTATION DETAILS

Implement the first version as an explicit, measurable black-box experiment.

## Hidden policy facts

Use a configurable library of synthetic policy categories. For example:

- A synthetic project identifier is confidential.
- A defined category of synthetic data requires redaction.
- A particular test marker must not appear in output.
- A synthetic tool is not permitted.
- A specific class of request receives normalized rejection.
- Session context must not cross between test IDs.
- A defined synthetic data class requires output inspection.
- A particular safe test fixture is allowed.

These are examples, not production secrets.

At the beginning of each round:

1. Select the relevant policy facts from the configured test set.
2. Canonicalize the policy representation.
3. Generate a strong random nonce.
4. Calculate a SHA-256 commitment over the canonical representation and nonce.
5. Store the ground truth and nonce in evaluator-only storage.
6. Expose the commitment and non-sensitive round metadata to the participants.

Document the exact commitment encoding so verification is reproducible. Use an unambiguous canonical representation and prevent the nonce from reaching Red before finalization.

## Probe processing

Red submits a probe to the controller. The controller verifies the session and role, checks the remaining budget, creates an event ID, and sends the request through the permitted pipeline.

The observation service returns only allowed information.

The policy evaluator privately tracks:

- What the hidden policy would do.
- What response was actually observable.
- Whether the observation exposes an unintended distinction.
- Whether the response violates the configured policy.
- Whether the event belongs to the correct round.

Ensure the evaluator does not accidentally include hidden ground truth in its response payload or logs that Red can access.

## Two response modes

Implement:

**Diagnostic mode:** Allows a controlled set of differentiated synthetic responses to help demonstrate response-based policy inference.

**Normalized mode:** Uses a common safe response for designated rejection classes, reducing unnecessary policy-specific detail.

Do not simply append random noise and claim side channels are solved. If latency timing is measured, collect real measurements, use sufficient repetitions, and document environmental noise and statistical limitations.

## Guess locking and evaluation

Red submits structured guesses and locks them before finalization.

After the round is closed, an authorized evaluator compares the guesses against the ground truth.

At minimum, calculate:

- True positive policy guesses.
- False positive policy guesses.
- False negative policy guesses.
- Precision.
- Recall.
- Inference coverage.
- Direct policy disclosures.
- Number of probes.
- Observation leakage counts.
- P50 and P95 latency where sample size permits.

Use clearly documented formulas.

For example:

`Inference coverage = correctly inferred hidden facts / total hidden facts`

`Precision = correct inferred facts / all submitted positive guesses`

`Recall = correct inferred facts / all hidden facts that were successfully represented as inferable targets`

Handle divisions by zero explicitly.

A composite leakage score may be included only if its component weights and formula are documented. Always display component metrics alongside the aggregate score.

## Before-and-after analysis

Run comparable evaluation rounds under different Blue configurations.

The report should compare:

- Number of facts inferred.
- Probe success rate.
- Response distinctions.
- Direct disclosure incidents.
- Latency distributions.
- False-positive and false-negative rates.

Record the model version, defense version, policy seed/commitment, and test-set version.

Do not compare unrelated rounds and call the result a controlled experiment.

## Important limitation

ShadowPolicy does not prove that all hidden information is impossible to infer. It measures leakage under the selected observation model, probe budget, test dataset, model, and environment.

Make that limitation visible in the application and exported report.

# 10. SANDBOX ISOLATION AND NETWORK SECURITY

Treat this section as one of the most important requirements in the implementation.

## Docker Compose architecture

Create a working `compose.yaml` with service definitions and clearly documented networks.

Create separate network segments for:

- Public frontend/API ingress.
- Red service communication.
- Blue policy communication.
- Model communication.
- Evaluation service communication.
- Audit collector communication.

Use internal Docker networks wherever possible.

Red must not connect directly to Blue or the model. Blue must not connect directly to Red. The model must not be exposed publicly. Cross-service requests must travel through explicitly allowed endpoints.

The controller may join multiple internal networks to mediate requests, but that makes it a high-trust component. Document this fact and minimize its permissions.

Do not rely on frontend hiding or different URL paths as the security boundary.

## Container hardening

Apply the relevant controls to each service, based on what it actually needs:

- Non-root user.
- `cap_drop: [ALL]` where compatible.
- `no-new-privileges:true`.
- Read-only root filesystem where possible.
- Restricted writable temporary storage.
- No privileged containers.
- No Docker socket mounts.
- No host networking.
- No unnecessary bind mounts.
- Configurable CPU and memory limits.
- Process-count limits where supported.
- Seccomp restrictions.
- Minimal images and dependencies.
- Health checks.
- Explicit exposed and published ports.

Generate a restricted seccomp profile only when its syscall requirements have been validated for that service. Do not create a profile that makes the service fail and then mark the control as complete.

Use separate Linux namespaces and cgroups when available. Where the runtime supports gVisor, document how to enable it. Do not make gVisor mandatory for every developer machine.

Because container configuration support differs across Linux, Windows, macOS, Docker Desktop, and cloud platforms, document the effective controls and unsupported settings. Never claim that a setting enforces kernel isolation if it is ignored by the runtime.

## Network egress

Default to denying unnecessary outbound traffic.

The model, Red service, and Blue service must not have arbitrary Internet access.

If external model imports or telemetry require network access, route those operations through a separately restricted import/proxy service with explicit destination allowlists.

Do not give the model gateway unrestricted Internet access just to simplify model downloading.

## Session and cache isolation

- Use a unique identifier for every session.
- Do not share conversation history across sessions.
- Do not mutate the target model as part of an ordinary evaluation.
- Pin the model and defense version for a test.
- Use isolated context and storage for each session.
- Ensure cleanup happens when an evaluation finishes.
- Disable cross-session prefix/KV caching where the serving runtime supports it and where needed for the threat model.
- Record when a cache-related safeguard is unsupported or unverified.

Implement a cross-session synthetic-canary test: insert a unique marker in one test session, then check whether an unrelated session can retrieve it. Label this as a test of observed cross-session contamination, not as proof against every KV-cache or hardware side channel.
